# Методика экспериментального исследования

Документ описывает назначение тестовой нагрузки, параметры запуска и рекомендуемый протокол. Фактические параметры каждого эксперимента следует брать из `experiment-info.txt`, JSONL/CSV и конфигурации запуска, а не восстанавливать по значениям по умолчанию.

## 1. Объект и границы эксперимента

Объект исследования — поведение сборщиков мусора Go runtime, CLR (.NET 10) и HotSpot JVM при заданных синтетических профилях выделения и времени жизни объектов.

Эксперимент сравнивает реакцию runtime на контролируемую нагрузку, а не производительность языков программирования вообще. Логическая структура тестовых сценариев согласована, однако физическое представление объектов и служебные расходы runtime различаются.

Прикладную нагрузку создаёт один основной поток/горутина. Внутренние потоки GC могут работать параллельно. Поэтому результаты не характеризуют многопоточные серверные нагрузки.

## 2. Сценарии нагрузки

- **transient** — создание массива узлов с последующей потерей ссылок; профиль краткоживущих объектов.
- **retained** — в каждом измеряемом батче создаются `items` узлов; около 10% остаются достижимыми до конца запуска. Удерживаемый набор накапливается между батчами.
- **graph** — создание узлов с циклическими и перекрёстными ссылками; после обработки граф становится недостижимым.
- **large** — создание и освобождение массивов байтов заданного размера. При стандартном `payload=128` это небольшие массивы, не предназначенные для проверки LOH/humongous allocation.
- **mixed** — удержание примерно 10% узлов каждого батча и освобождение остальных узлов вместе с дополнительным буфером `max(1, payload*16)`. Удерживаемый набор накапливается.

Для исследования LOH .NET используйте размер массива выше порога LOH и фиксируйте точный размер. Для humongous-объектов G1 размер должен быть выбран относительно размера региона и параметров heap. Автоматическая серия 1 MiB является отдельной экспериментальной конфигурацией; не объединяйте её с базовой серией 128 байт без явного разделения факторов.

## 3. Параметры

Основные аргументы:
- `scenario` — один из пяти сценариев;
- `warmup-batches` — число прогревочных батчей;
- `batches` — число измеряемых батчей;
- `items` — число узлов/массивов в батче;
- `payload` — размер полезной нагрузки в байтах.

Параметры по умолчанию: 50 прогревочных батчей, 1 000 измеряемых батчей, 10 000 узлов/массивов и 128 байт полезной нагрузки. Это исходные настройки, а не универсально оптимальные параметры.

Прогрев повторяет сценарий, включая удержание объектов в `retained`/`mixed`, создание буфера в `mixed` и чтение содержимого. Затем ссылки очищаются и выполняется подготовительная полная сборка, не включаемая в измеряемые дельты. Прогрев снижает влияние JIT-компиляции, но не доказывает полной стабилизации оптимизированного кода. Чувствительность к прогреву проверяйте отдельными сериями, например:

```bat
tools\run_warmup_sensitivity.bat 5 10000 1000 128 "0 10 50 100"
```

Не объединяйте результаты разных уровней прогрева в одну статистическую группу.

## 4. Полный запуск в Windows

Из корня репозитория:

```bat
RUN_ALL_GC_EXPERIMENTS.bat
```

Или с параметрами:

```bat
RUN_ALL_GC_EXPERIMENTS.bat [runs] [items] [batches] [payload]
```

Сценарий проверяет Python 3.10+, Go, .NET 10 SDK, JDK 21+ с `javac`/`jfr` и `dotnet-trace`; выполняет базовую матрицу, отдельные диагностические запуски и серию крупных массивов. Порядок платформ для каждого сценария и повтора выбирается случайно; процессы выполняются последовательно. Каждый полный запуск создаёт новую папку результатов и файл `experiment-info.txt`.

Для пропуска дополнительной серии 1 MiB:

```bat
set SKIP_LARGE_OBJECT_SERIES=1
```

Для EventPipe требуется:

```powershell
dotnet tool install --global dotnet-trace
```

## 5. Ручные запуски

### Go

Требуется Go 1.20 или новее.

```bash
cd go
go version
go build -o gcbench .
./gcbench -scenario transient -warmup-batches 50 -batches 1000 -items 10000 -payload 128
```

Результат — JSON-строка в stdout. Дополнительный GC trace направляйте в отдельный файл stderr:

```bash
GODEBUG=gctrace=1 ./gcbench -scenario transient ... 1>go.jsonl 2>go-gc-trace.log
```

Фиксируйте `GOGC`, `GOMEMLIMIT` и `GOMAXPROCS`.

### .NET 10

Проект собирается под `net10.0`; для сборки нужен .NET 10 SDK, для запуска — .NET 10 Runtime. Проверьте установленные версии:

```powershell
dotnet --info
dotnet --list-sdks
dotnet --list-runtimes
```

Перед экспериментом фиксируйте режим GC (Workstation/Server), настройки runtime и переменные среды. Не сравнивайте разные режимы как один и тот же вариант конфигурации.

### Java

Требуется JDK 21+ с `javac` и `jfr`.

```bash
cd java
javac GcBench.java
java -Xms512m -Xmx512m GcBench --scenario transient --warmup-batches 50 --batches 1000 --items 10000 --payload 128
```

Для отдельных сравнений сборщиков запускайте самостоятельные серии с явно указанными JVM-флагами, например G1, Parallel GC или ZGC. Конкретная доступность сборщика зависит от сборки JDK. Не формулируйте выводы как характеристики «Java вообще»: каждый результат относится к конкретной JVM и выбранной конфигурации GC.

## 6. Повторы и статистическая обработка

1. Зафиксируйте CPU, число ядер/потоков, RAM, ОС, архитектуру, версии runtime и параметры GC.
2. Выполняйте каждый сценарий в отдельном процессе; рекомендуется не менее 10 независимых повторов.
3. Сохраняйте исходные JSONL/CSV и метаданные каждого запуска.
4. Сначала анализируйте повторы внутри одной сессии и одной конфигурации. Повторите полный эксперимент как минимум в трёх новых сессиях, чтобы оценить межсессионный дрейф.
5. Основные сводки представляют медиану и IQR между независимыми процессными повторами. Доверительный интервал указывайте отдельно с методом вычисления и числом повторов.
6. p50/p95/p99 задержек батчей рассчитываются внутри отдельного запуска и не заменяют статистику между независимыми запусками.
7. Не объединяйте разные `session_id`, версии схемы, размеры payload, прогревы или конфигурации GC в одну статистическую выборку.

Скрипт суммирования:

```bash
python tools/summarize.py results/go-transient.jsonl results/dotnet-transient.jsonl results/java-transient.jsonl -o results/comparison.csv
```

Визуализация CSV:

```bash
python tools/visualize_results.py results/comparison.csv -o results/report --split-by-scenario
```

Проверяйте параметры и поддерживаемые аргументы скриптов по их `--help` и текущему исходному коду перед запуском.

## 7. Системная память и CPU

Внутренние показатели heap/committed не равны RSS: RSS/Working Set включает нативную память, стеки, JIT-код, метаданные и другие области процесса.

Для Linux:

```bash
/usr/bin/time -v ./gcbench -scenario transient ...
pidstat -r -u -p <PID> 1
```

Для Windows:

```powershell
Get-Process -Id <PID> | Select-Object Id, WorkingSet64, PeakWorkingSet64, CPU
```

Для macOS можно использовать `/usr/bin/time -l`. В отчёте указывайте ОС и конкретный инструмент. Встроенный внешний sampler проекта использует интервал 50 мс; пик относится ко всему времени жизни процесса, включая запуск, прогрев и очистку, а не только к измеряемому окну. Среднее значение является выборочным, а мониторинг может влиять на планирование.

## 8. Ограничения

- Сценарии функционально похожи, но физическое представление объектов и runtime overhead различаются.
- `payload_bytes_requested` — заданный размер полезной нагрузки, а не фактический размер heap.
- Счётчики аллокаций, GC и пауз имеют разный охват и семантику; см. [описание метрик](metrics.md).
- Инструментированные JFR/EventPipe-запуски отделены от базовых измерений производительности.
- Принудительные сборки используются в подготовительных/диагностических фазах и не должны интерпретироваться как часть штатной нагрузки.
- Синтетические результаты не доказывают превосходство языка/runtime в произвольном приложении.
