# Измеряемые показатели и правила интерпретации

## 1. Матрица показателей

| Группа | Go | C# / .NET 10 | Java / HotSpot |
|---|---|---|---|
| Аллокации | `runtime.MemStats.TotalAlloc`, process-wide | `GC.GetTotalAllocatedBytes`, process-wide managed allocations | `ThreadMXBean.getTotalThreadAllocatedBytes()` и отдельный счётчик потока теста |
| Состояние heap | `HeapAlloc`, `HeapSys`, `HeapInuse` | `GC.GetTotalMemory`, `GCMemoryInfo.TotalCommittedBytes` | `MemoryMXBean` used/committed |
| Число сборок | `NumGC` | `GC.CollectionCount(0..2)` | `GarbageCollectorMXBean` по коллекторам |
| Суммарные паузы | `PauseTotalNs` | `GC.GetTotalPauseDuration()` | JFR `jdk.GCPhasePause` в отдельной диагностической записи |
| Распределение пауз | Дельта `/sched/pauses/total/gc:seconds`, оценка по buckets | EventPipe suspend/resume и fully-suspended интервалы | JFR `jdk.GCPhasePause` |
| CPU GC | `/cpu/classes/gc/total:cpu-seconds`, runtime estimate | Отдельный анализ EventPipe/PerfView | Отдельный профилировщик; MXBean collection time не является CPU time |
| Задержки | p50/p95/p99 батчей | p50/p95/p99 батчей | p50/p95/p99 батчей |
| Системная память | Внешний sampler | Working Set snapshot и внешний sampler | Внешний sampler |

## 2. Аллокации

Счётчики имеют различный охват:
- Go `TotalAlloc` — накопленные выделения runtime процесса.
- .NET `GetTotalAllocatedBytes` — управляемые выделения процесса.
- Java `getTotalThreadAllocatedBytes()` — приблизительный суммарный счётчик heap-аллокаций потоков JVM с момента запуска; проект дополнительно сохраняет показатель потока бенчмарка.

Java ThreadMXBean не измеряет нативные выделения JVM, JIT-код или полную память процесса. Суммарное значение приблизительное; точность и поддержка зависят от JVM. В проекте отдельно проверяется учёт аллокаций завершившегося worker-потока. Не описывайте счётчик как размер только активных потоков.

**Все три значения runtime-specific и не являются строго сопоставимыми.** Не стройте на их основе единый рейтинг платформ и не приравнивайте их к RSS. Указывайте scope каждого поля и сохраняйте флаг `cross_platform_comparable=false`, если он присутствует в данных.

## 3. Счётчики сборок и времени

Числа сборок также не образуют общей шкалы: Go `NumGC` считает циклы, .NET предоставляет счётчики по поколениям, Java — показатели отдельных MXBean-коллекторов. Сравнивайте их внутри конкретного runtime и конфигурации.

Go `PauseTotalNs` — суммарное STW-время runtime. .NET `GC.GetTotalPauseDuration()` — суммарное время пауз управляемых потоков. Java `GarbageCollectorMXBean.getCollectionTime()` — приблизительное elapsed-время коллектора, но не эквивалент STW и не CPU-время потоков GC.

Go `/cpu/classes/gc/total:cpu-seconds` является оценочным runtime-показателем, а не прямым эквивалентом системного CPU time. Сравнивать его напрямую с CPU-секундами профилировщика другой платформы нельзя.

## 4. Индивидуальные паузы

- **Go:** распределение оценивается по дельте гистограммы `/sched/pauses/total/gc:seconds` за измеряемый интервал. Процентили восстановлены по bucket-границам и являются приближёнными. Не следует выдавать их за точные длительности отдельных событий.
- **.NET:** EventPipe фиксирует интервал `GCSuspendEEStart` → `GCRestartEEStop`; отдельно `fully_suspended_ms` соответствует интервалу `GCSuspendEEStop` → `GCRestartEEStart`. Это разные временные определения; в публикации указывайте, какое используется. Поколение и тип GC связываются с событиями GCStart.
- **Java:** JFR использует верхнеуровневое событие `jdk.GCPhasePause`. Не суммируйте его с вложенными `jdk.GCPhasePauseLevel*`, чтобы не получить двойной учёт.

Источники событий и определения интервалов различаются. Не сравнивайте межплатформенные p50/p95/p99 GC-пауз как строго эквивалентные показатели. Инструментированные JFR/EventPipe-запуски предназначены для диагностики распределения пауз, а не для замены базовых измерений времени выполнения.

## 5. Задержки батчей и пропускная способность

`batch_latency_ms` — время обработки одного батча синтетической нагрузки. Оно включает работу прикладного кода, аллокатора и воздействие GC; это не чистое время GC и не задержка HTTP-запроса.

`logical_nodes_per_second` и `payload_bytes_per_second` характеризуют интенсивность синтетической нагрузки, а не пропускную способность реального сервиса. В сценарии `large` корректнее отдельно указывать число созданных массивов в секунду и их заданный размер.

Проверяйте таймер и длительность окна. В Windows Go использует `QueryPerformanceCounter`, на других ОС — монотонный таймер Go. Сопоставление задержек требует одинаковой логики батча и достаточной длительности измерения.

## 6. Heap, committed и RSS/Working Set

- Heap used — состояние управляемой кучи в момент снимка; оно зависит от времени последней сборки.
- Heap committed — объём памяти, зарезервированный/закоммиченный runtime; это не RSS.
- RSS/Working Set включает память процесса за пределами управляемой кучи: нативные выделения, стеки, JIT-код, метаданные и прочее.
- `WorkingSet64` — точечный снимок, не пик.
- Внешний sampler проекта собирает значения с интервалом 50 мс. Пиковое значение относится ко всему времени жизни процесса, включая запуск, прогрев и очистку; это не пик строго измеряемого интервала. Среднее — выборочная оценка, не непрерывная интеграция.

Метрики системной памяти анализируйте отдельно от рейтингов производительности и обязательно указывайте инструмент, ОС и окно захвата.

## 7. Статистические единицы

Независимая единица основного сравнения — отдельный процессный запуск. Для него сохраняются задержки батчей и runtime deltas. Основные графики показывают медиану по независимым запускам и IQR. Доверительный интервал должен сопровождаться описанием метода и числа повторов.

Отдельные GC-паузы внутри одной трассы не являются независимыми экспериментальными повторами. Для вывода о различиях конфигураций сначала агрегируйте паузы на уровне запуска, затем сравнивайте распределения показателей между независимыми запусками. Различия между экспериментальными сессиями следует анализировать отдельно.
