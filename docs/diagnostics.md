# Диагностические трассы GC: EventPipe, JFR и Go

Диагностические трассы используются для анализа отдельных GC-пауз и проверки поведения runtime. Они собираются отдельно от базовых запусков времени выполнения, поскольку трассировка может добавлять overhead.

## 1. Общие правила

- Сохраняйте исходные `.nettrace`, `.jfr`, JSONL/CSV и статус обработки.
- Сопоставляйте трассу с точным процессным запуском, сценарием, конфигурацией и измерительным интервалом.
- Не используйте неполные трассы в статистической сводке.
- Отсутствие потерь событий не доказывает корректность классификации. Перед публикацией вручную проверьте репрезентативные записи независимым инструментом.
- Не смешивайте инструментированные диагностические показатели с базовыми wall-clock результатами.

## 2. .NET EventPipe

Для полного сценария требуется `dotnet-trace`:

```powershell
dotnet tool install --global dotnet-trace
```

EventPipe подписывается на GC-события CLR и маркеры границ измеряемого интервала. Отчёт должен проверять:
- `lostEvents`;
- `incompleteIntervals`;
- `unmatchedResumeCount`;
- `gcEventAssociationFailures`;
- `conflictingGcStartEvents`.

Для валидной трассы все перечисленные значения должны быть равны нулю. Дополнительно проверьте классификацию поколения, причины и типа GC. Контрольные трассы следует получить как минимум для:
- Workstation GC;
- Server GC;
- фоновой сборки Gen 2 (Background GC);
- нагрузки с выделением объектов в LOH.

Сверьте хотя бы одну трассу каждого существенного режима с независимым анализатором EventPipe/ETW, например PerfView. Автоматические проверки целостности не заменяют семантическую проверку событий.

### Интерпретация интервалов

- `duration_ms`: от `GCSuspendEEStart` до `GCRestartEEStop`, включая переход к остановке и возобновлению.
- `fully_suspended_ms`: от `GCSuspendEEStop` до `GCRestartEEStart`, период полной остановки среды выполнения.

Эти показатели нельзя называть одним и тем же временем STW без уточнения определения. Указывайте выбранный интервал в таблицах и тексте публикации.

## 3. Java JFR

Проект записывает ограниченный набор событий:
- `jdk.GCPhasePause`;
- `jdk.GarbageCollection`;
- `jdk.DataLoss`.

Наличие `jdk.DataLoss` означает неполную запись; такую трассу следует отклонить. При анализе используйте верхнеуровневое `jdk.GCPhasePause`; не суммируйте вложенные `jdk.GCPhasePauseLevel1/2/3` с верхнеуровневым событием.

JFR создаётся отдельным диагностическим запуском и имеет overhead. В текущей реализации запись начинается непосредственно перед подготовкой списка времён батчей и запуском измерительного таймера; короткий подготовительный фрагмент теоретически может попасть в JFR. При ручном анализе соотносите события с фактическим измерительным окном и не включайте события до него в распределение рабочей нагрузки.

GC log, включённый параметром `-Xlog:gc*`, начинается при старте JVM и включает прогревочную часть. Для отделения измеряемого интервала используйте временные метки из JSON, в частности `measurement_start_uptime_ms`, если поле присутствует.

Для пакетной обработки JFR в проекте предусмотрены скрипты:

```bat
tools\process_java_jfr.bat
tools\process_java_jfr.bat transient
```

Отчёт `jfr_pause_report.py` строит список событий и сводку пауз. Проверяйте доступные параметры скрипта через `--help`.

## 4. Go

Распределение пауз формируется по дельте гистограммы `/sched/pauses/total/gc:seconds` за измеряемый интервал. Гистограмма содержит counts по buckets, а не точные исходные длительности каждой паузы. Поэтому поля с суффиксом `_approx` — оценки по границам buckets.

Не следует использовать кольцевой буфер `PauseNs` как полный источник распределения: он ограничен количеством последних записей. Сохраняйте bucket counts и явно указывайте метод оценки квантилей.

## 5. Условия включения в публикацию

До включения диагностических результатов:
1. Проверьте отсутствие потерь/незакрытых интервалов.
2. Проверьте корректность привязки событий к измеряемому процессу и окну.
3. Сверьте классификацию GC с независимым анализатором.
4. Укажите, что JFR/EventPipe — отдельные инструментированные запуски.
5. Укажите точное определение паузы, способ расчёта квантилей и число пауз в каждой трассе.
6. Не трактуйте квантили, полученные разными инструментами и разными определениями интервала, как полностью сопоставимые.

Для научной публикации приводите только фактически проверенные конфигурации и результаты. Наличие сценария в документации не означает, что соответствующая контрольная трасса уже была выполнена.
