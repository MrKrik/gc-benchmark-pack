# Запуск полного эксперимента одной командой (Windows)

В корне распакованного проекта запустите двойным щелчком `RUN_ALL_GC_EXPERIMENTS.bat` либо из CMD: `RUN_ALL_GC_EXPERIMENTS.bat`.

Скрипт автоматически: (1) проверяет Python 3.10+, Go, .NET 10 SDK, JDK 21+ с `javac`/`jfr` и `dotnet-trace`; (2) запускает стандартную матрицу Go/.NET/Java по пяти сценариям; (3) запускает отдельные .NET EventPipe-процессы для сбора индивидуальных GC-пауз; (4) записывает JFR для пяти Java-сценариев; (5) анализирует обе диагностические серии и добавляет результаты в HTML-отчёты; (6) отдельно запускает серию крупных объектов размером 1 MiB для Go/.NET/Java, включая отдельную .NET EventPipe-диагностику, затем строит сравнительные таблицы и графики. Каждый runtime компилируется один раз. В стандартной матрице для каждого сценария порядок платформ случайно выбирается заново на каждом повторе; задание остаётся последовательным, без одновременных benchmark-процессов.

Каждый запуск сохраняется в новой папке `results\run_YYYYMMDD_HHMMSS_<random>`, поэтому предыдущие серии не перезаписываются. Внутри папки есть `experiment-info.txt` с версиями инструментов и конфигурацией. Для изменения параметров можно передать четыре аргумента: `RUN_ALL_GC_EXPERIMENTS.bat [runs] [items] [batches] [payload]`. По умолчанию это `10 10000 1000 128`; увеличение числа батчей даёт примерно секундное или более длинное окно измерения. Чтобы пропустить дополнительную серию 1 MiB (она полезна для проверки LOH .NET и humongous objects G1), предварительно выполните `set SKIP_LARGE_OBJECT_SERIES=1`.

**Важно:** JFR Java и EventPipe .NET собираются в отдельных инструментированных процессах, не смешанных с базовыми показателями времени. JFR записывает только `jdk.GCPhasePause`, `jdk.GarbageCollection` и `jdk.DataLoss`; наличие `jdk.DataLoss` отклоняет запись как неполную. EventPipe подписан на GC-события CLR и узкие маркеры границ измеряемого интервала. Отчёт проверяет потери событий и незакрытые интервалы пауз; неполная трасса прерывает эксперимент. Для EventPipe требуется `dotnet-trace` (установка: `dotnet tool install --global dotnet-trace`). Базовые процессы дополнительно сопровождаются внешним сборщиком Working Set: интервал выборки — 50 мс, Windows использует системный пик PSAPI, Linux — kernel `VmHWM`, а macOS — максимальную периодическую выборку. Среднее является выборочным. Эти показатели вынесены в отдельные диагностические графики; мониторинг может слегка влиять на планирование процесса. В 1 MiB серии базовая сравнительная таблица использует Go/.NET/Java без профилировщика и со стандартными JVM-настройками; конфигурации Java имеют отдельные `runtime_configuration_id`, а JFR с фиксированными настройками G1 и .NET EventPipe остаются отдельной диагностикой.

# Набор тестов для исследования Garbage Collector: Go, .NET и Java

Набор предназначен для воспроизводимого сбора показателей GC в трёх средах выполнения. Он не является полноценным промышленным benchmark-фреймворком: его задача — создать контролируемые профили объектов и сохранить машинно-читаемые результаты для дальнейшего анализа.

## 1. Что измеряется

| Показатель | Go | C# / .NET | Java / HotSpot |
|---|---|---|---|
| Выделенная managed/heap-память за измерение | `runtime.MemStats.TotalAlloc` процесса | `GC.GetTotalAllocatedBytes` процесса | `ThreadMXBean.getTotalThreadAllocatedBytes()` для живых Java-потоков; отдельно сохраняется счётчик потока теста |
| Размер кучи | `HeapAlloc`, `HeapSys`, `HeapInuse` | `GC.GetTotalMemory`, `GCMemoryInfo.TotalCommittedBytes` | `MemoryMXBean` used/committed |
| Частота сборок | `NumGC` | `GC.CollectionCount(0..2)` | `GarbageCollectorMXBean` по каждому коллектору |
| Суммарное STW-время | `PauseTotalNs` | `GC.GetTotalPauseDuration()` | JFR `jdk.GCPhasePause` в отдельном диагностическом запуске |
| Индивидуальные STW-паузы | Оценочное распределение по дельте `/sched/pauses/total/gc:seconds` | EventPipe: полная пауза `GCSuspendEEStart` → `GCRestartEEStop`; отдельно длительность полной остановки runtime, тип и поколение из `GCStart` | JFR `jdk.GCPhasePause` |
| Время GC как доля CPU | Оценка `/cpu/classes/gc/total:cpu-seconds` | Отдельный EventPipe/PerfView-анализ; `time-in-gc` — это паузы, не CPU-время GC | Отдельный JFR/профилировщик; MXBean collection time — не CPU-время GC |
| Логическая интенсивность тестовой нагрузки | узлы/с, байты payload/с, managed bytes/с | узлы/с, байты payload/с, managed bytes/с | узлы/с, байты payload/с, байты потока теста/с |
| Задержки батчей | p50/p95/p99 | p50/p95/p99 | p50/p95/p99 |
| RSS/Working Set | внешний системный инструмент | Working Set в момент снимка + внешний пик | внешний системный инструмент |

**Важно:** показатели с одинаковым названием не всегда имеют одинаковую семантику и охват. Go считает process-wide runtime allocations, .NET — managed allocations процесса, Java — байты, выделенные всеми Java-потоками согласно `ThreadMXBean`; проверено, что счётчик сохраняет аллокации дополнительного потока и после его завершения. Значение Java не включает JVM-служебные нативные выделения. Исходный счётчик главного потока также сохраняется. Аллокации помечены как несопоставимые и показываются раздельно по платформам. Java `GarbageCollectorMXBean.getCollectionTime()` — приблизительное elapsed-время отдельного коллектора, не STW-время и не CPU-время потоков GC; отчёт оставляет такие счётчики раздельными.

Java сохраняет два счётчика аллокаций: суммарный `getTotalThreadAllocatedBytes()` и исходный `getThreadAllocatedBytes()` для потока бенчмарка. Первый охватывает Java-потоки, а не всю нативную память или внутренние выделения JVM; оба счётчика остаются runtime-specific.

Go `/cpu/classes/gc/total:cpu-seconds` — оценочный runtime-показатель и, согласно документации Go, не является прямым эквивалентом системного CPU time. Сравнивать его напрямую с CPU-секундами профилировщика другой платформы нельзя.

В Windows Go измеряет длительность каждого батча и полное измеряемое окно через `QueryPerformanceCounter`; на других ОС используется монотонный таймер Go. Поэтому процентили батчей больше не ограничены миллисекундной гранулярностью. Два чтения QPC на батч добавляют небольшую стоимость измерения; при очень коротких батчах увеличьте `items` или `batches`.

## 2. Сценарии

Все три программы используют одинаковые имена сценариев и аргументы:

- `transient` — каждую итерацию создаётся массив узлов и сразу теряется ссылка на него; моделирует поток краткоживущих объектов.
- `retained` — в каждом измеряемом батче создаются `items` узлов; около 10% равномерно выбираются и остаются достижимыми до конца запуска, остальные освобождаются. Набор накапливается между батчами, поэтому этот сценарий проверяет выживание и рост долгоживущей кучи, а не только временные выделения.
- `graph` — создаются узлы с циклическими и перекрёстными ссылками; после обработки граф становится недостижимым.
- `large` — создаются и освобождаются массивы байтов. При стандартном `payload=128` это небольшие массивы, не LOH/humongous-объекты; для проверки LOH .NET задайте `--payload 100000` или больше, а размер для humongous-объектов G1 выбирайте с учётом размера региона и явно указывайте JVM/heap-параметры.
- `mixed` — в каждом измеряемом батче удерживается примерно 10% созданных узлов (как минимум один), остальные узлы и дополнительный буфер размером `max(1, payload*16)` освобождаются. При стандартном `payload=128` это всего 2 KiB, не LOH/humongous-объект. Удерживаемый набор накапливается между батчами и к концу измерения растёт; это модель нагрузки с долгоживущей долей.

Аргументы:

- `--scenario`: один из пяти сценариев;
- `--batches`: количество измеряемых батчей;
- `--warmup-batches`: количество прогревочных батчей, не включаемых в разницу счётчиков;
- `--items`: число узлов/массивов в батче или размер долгоживущего набора;
- `--payload`: число байт полезной нагрузки в каждом узле; для `large` — размер каждого массива.

По умолчанию: 50 прогревочных батчей, 1 000 измеряемых батчей, 10 000 узлов на батч, 128 байт полезной нагрузки на узел. Прогрев повторяет сценарий: включая удержание части узлов в `retained`/`mixed`, буфер в `mixed` и чтение содержимого. Затем ссылки очищаются и выполняется контролируемая полная сборка до измерения. Прогрев снижают влияние Tiered JIT в .NET и компиляции HotSpot, но не доказывает стабилизацию оптимизированного кода; проверяйте чувствительность результатов отдельными сериями, например через `run_warmup_sensitivity.bat`. Измеряемое окно обычно становится порядка секунды или дольше; фактическое время зависит от сценария и runtime. Для `retained` и `mixed` около 10% узлов каждого батча остаётся в памяти, поэтому по умолчанию удерживаемый набор может вырасти примерно до миллиона узлов. Это стартовые параметры, а не универсально оптимальные значения. Перед основной серией проверьте, что процесс не уходит в swap и не завершается по OOM.

Прогрев заканчивается запросом принудительной полной сборки, которая не включается в измеряемые счётчики. В JVM тест отказывается запускаться с `-XX:+DisableExplicitGC` и ожидает роста MXBean-счётчика сборок после `System.gc()` перед снимком heap. Если завершённая сборка не наблюдается за 60 секунд, результат не выдаётся. После измерения такой же подтверждённый запрос используется для снимка живой кучи; эта диагностическая сборка исключена из счётчиков нагрузки. Сами запросы GC различаются между runtime, их нельзя трактовать как часть результата.

`retained_nodes_after` показывает число узлов, оставшихся достижимыми в конце запуска. В `mixed` удерживается та же доля узлов, что и в `retained`, плюс на каждом батче создаётся дополнительный буфер; сравнение этих сценариев изолирует влияние краткоживущих буферов. Чтобы исследовать LOH/humongous allocations, задайте размеры массивов выше порога соответствующей среды и зафиксируйте настройки GC.

Для проверки влияния прогрева запустите отдельную серию с несколькими значениями прогревочных батчей. Скрипт сохраняет каждое значение в отдельную сессию/папку и создаёт полный набор HTML/CSV:

```bat
tools\run_warmup_sensitivity.bat 5 10000 1000 128 "0 10 50 100"
```

Для стабильного вывода сравнивайте повторы отдельно для каждого значения прогрева; не объединяйте строки из разных сессий в один доверительный интервал.

## 3. Сборка и запуск

### Go

Требуется Go 1.20 или новее.

```bash
cd go
go version
go build -o gcbench .
./gcbench -scenario transient -warmup-batches 50 -batches 1000 -items 10000 -payload 128
```

Результат — одна JSON-строка в stdout. Для сохранения десяти повторов:

```bash
for i in $(seq 1 10); do
  ./gcbench -scenario transient -warmup-batches 50 -batches 1000 -items 10000 -payload 128 >> go-transient.jsonl
done
```

Для дополнительного журнала GC можно задать `GODEBUG=gctrace=1`; такие строки идут в stderr и должны сохраняться отдельно от JSON:

```bash
GODEBUG=gctrace=1 ./gcbench -scenario transient ... 1>>go-transient.jsonl 2>>go-gc-trace.log
```

Настройки Go фиксируйте отдельно: `GOGC`, `GOMEMLIMIT`, `GOMAXPROCS`. Пример запуска с memory limit:

```bash
GOGC=100 GOMEMLIMIT=768MiB GOMAXPROCS=4 ./gcbench -scenario transient ...
```

Если удобнее использовать обычную командную строку Windows (`cmd.exe`), запускайте `tools\run_repeat.bat`. Скрипт собирает выбранную программу один раз, затем выполняет указанное число независимых запусков и записывает JSONL в `results\<платформа>-<сценарий>.jsonl`.

Параметры: платформа, сценарий, число запусков, число объектов, число батчей и размер полезной нагрузки. Последние четыре параметра необязательны; значения по умолчанию: `10 10000 1000 128`. По умолчанию выполняется 50 прогревочных батчей; их число можно переопределить переменной окружения:

`JAVA_OPTS` предназначена для JVM-флагов, разделённых пробелами; не используйте в ней значения свойств, содержащие пробелы. ```


Для автоматизации повторов из корня архива:

```bash
./tools/run_repeat.sh dotnet transient 10 10000 1000 128
```

Сравните Workstation GC и Server GC в отдельных сериях. Например, на Linux/macOS:

```bash
DOTNET_gcServer=0 dotnet bin/Release/net10.0/GC.Bench.dll --scenario transient ...
DOTNET_gcServer=1 dotnet bin/Release/net10.0/GC.Bench.dll --scenario transient ...
```

Не смешивайте результаты двух режимов в одной группе. Сохраняйте `dotnet --info`, переменные окружения и runtimeconfig проекта.

Для наблюдения за работающим процессом:

```bash
dotnet-counters ps
dotnet-counters monitor --process-id <PID> System.Runtime
```

В первую очередь полезны `Allocation Rate`, `GC Heap Size`, `Gen 0/1/2 GC Count`, `% Time in GC` и `CPU Usage`. Обратите внимание: `% Time in GC` показывает долю времени пауз, а не процессорное время, потраченное фоновыми потоками GC. Для трассировки событий GC можно собрать EventPipe trace:

```bash
dotnet-trace collect --process-id <PID> --profile gc-verbose --duration 00:00:30 --output dotnet-gc.nettrace
```

Трассу можно анализировать в PerfView или совместимом анализаторе EventPipe/ETW.

### Java / HotSpot JVM

Требуется JDK 21 или новее: тест использует `ThreadMXBean.getTotalThreadAllocatedBytes()`, появившийся в JDK 21. BAT-файлы проверяют версию `javac` до компиляции.

```bash
cd java
javac GcBench.java
java -Xms512m -Xmx512m GcBench --scenario transient --warmup-batches 50 --batches 1000 --items 10000 --payload 128
```

Для GC log и JFR одновременно:

```bash
java -Xms512m -Xmx512m -Xlog:gc*:file=java-gc.log:time,uptime,level,tags \
  GcBench --scenario transient --warmup-batches 50 --batches 1000 --items 10000 --payload 128 --jfr-file java-gc.jfr
```

Посмотреть события пауз:

```bash
jfr print --events jdk.GCPhasePause java-gc.jfr > java-gc-pauses.txt
python ../tools/jfr_pause_report.py java-gc.jfr -o java-gc-pauses.csv --jfr-command "C:\Program Files\Java\jdk-24\bin\jfr.exe"
```

Второй вариант дополнительно считает число событий, сумму пауз, p50/p95/p99 и максимум, а также отклоняет запись с событием `jdk.DataLoss`. JFR создаётся самой тестовой программой после прогрева и очистки; включаются только `jdk.GCPhasePause`, `jdk.GarbageCollection` и `jdk.DataLoss` с нулевым порогом и без stack traces. Запись останавливается сразу после завершения измеряемого цикла, до чтения диагностических MXBeans и снимков памяти. Даже узкая запись имеет overhead и годится для диагностики пауз, а не для базовых сравнений производительности. GC log, если он включён флагом `-Xlog`, начинается при старте JVM и содержит также прогревочную часть; при анализе отделите её от измерения по `measurement_start_uptime_ms` из JSON.

Алгоритмы запускайте отдельными сериями, например:

```bash
java -XX:+UseG1GC ... GcBench --scenario transient ...
java -XX:+UseParallelGC ... GcBench --scenario transient ...
java -XX:+UseZGC ... GcBench --scenario transient ...
```

Доступность конкретного GC зависит от версии и сборки JDK. Не утверждайте, что тест характеризует «Java вообще»: каждый результат относится к указанной JVM и выбранному сборщику. Для повторов можно использовать `./tools/run_repeat.sh java transient 10 10000 1000 128`; выбранные JVM-флаги передаются через переменную `JAVA_OPTS`, например `JAVA_OPTS='-Xms512m -Xmx512m -XX:+UseG1GC'`.

После запуска нескольких серий объединить JSONL-файлы в CSV можно так:

```bash
python tools/summarize.py results/go-transient.jsonl results/dotnet-transient.jsonl results/java-transient.jsonl -o results/comparison.csv
```

На Windows все пять сценариев для Go, .NET и Java можно последовательно запустить одной командой из каталога `tools`:

```bat
run_all_scenarios.bat [повторы] [узлы] [батчи] [payload]
```

Например, `run_all_scenarios.bat 10 10000 1000 128` запустит 10 повторов каждого сочетания платформы и сценария в отдельной папке эксперимента. Для каждого повторения случайно выбирается одна из шести перестановок Go/.NET/Java; все процессы идут последовательно. После завершения будут созданы CSV и HTML-отчёты внутри папки `results/run_manual_…`; откройте `report-all/index.html`.

Для уже собранного CSV можно отдельно создать отчёты:

```bash
python tools/visualize_results.py results/comparison.csv -o results/report --split-by-scenario
```

Чтобы добавить к HTML-страницам сценариев уже обработанные данные JFR, укажите папку `jfr-analysis`:

```bash
python tools/visualize_results.py results/comparison-all-scenarios.csv -o results/report-all --split-by-scenario --jfr-analysis-dir results/jfr-analysis
```

Графики включают пропускную способность, время выполнения, скорость аллокаций и p50/p95/p99 `batch_latency_ms` для каждой платформы, включая Java. В сценарии `large` вместо нулевого числа узлов отображается скорость создания массивов в секунду (`large_buffers_created / elapsed_ms`). Если передан `--jfr-analysis-dir`, HTML-страница сценария также показывает медиану и квартильный диапазон числа и длительности Java STW-пауз из JFR и сводку по отдельным записям. Задержки `batch_latency_ms` относятся к целому батчу и не являются распределением отдельных GC-пауз.

## 4. Измерение RSS и CPU процесса

Программа выводит внутренние показатели runtime. Пиковый RSS лучше измерять внешним инструментом, потому что у runtime-метрик разные определения committed/used heap, а RSS включает также нативную память, стеки, JIT-код, метаданные и другие области процесса.

Linux:

```bash
/usr/bin/time -v ./gcbench -scenario transient ... 2> go-time.txt
```

Или в отдельном терминале:

```bash
pidstat -r -u -p <PID> 1
```

`/usr/bin/time -v` выдаёт максимальный resident set size для завершившегося процесса. `pidstat` показывает динамику RSS и общего CPU процесса, но не отделяет CPU GC от CPU приложения.

Windows PowerShell (снимок процесса, не непрерывная трасса):

```powershell
Get-Process -Id <PID> | Select-Object Id, WorkingSet64, PeakWorkingSet64, CPU
```

На macOS используйте `/usr/bin/time -l` для максимального resident set size. Для научного отчёта явно указывайте ОС и инструмент.

## 5. Протокол эксперимента

1. Зафиксируйте модель CPU, число ядер/потоков, RAM, ОС, архитектуру, версии Go/.NET/JDK и сборщик Java.
2. На первом этапе запустите каждую платформу с настройками по умолчанию. Сохраните параметры среды и запуска.
3. Выполните каждый сценарий отдельно, в новом процессе, не менее 10 раз. Сохраняйте все JSON-строки, не только агрегаты. `tools\run_all_scenarios.bat` компилирует каждый runtime один раз и случайно выбирает порядок платформ заново для каждого повторения; все процессы выполняются последовательно. В JSONL записываются `session_id`, номер повтора и выбранный `run_order`.
4. Повторите серии с заранее выбранными конфигурациями GC: например, Go с указанными `GOGC`/`GOMEMLIMIT`, .NET Workstation и Server, Java G1/Parallel/ZGC. Не меняйте одновременно несколько факторов.
5. Сравнение сначала проводите внутри одного сценария и одной группы конфигураций. Затем анализируйте компромиссы между группами.
6. Основные графики показывают медиану независимых запусков и IQR (Q1–Q3 по линейной интерполяции PERCENTILE.INC); отчёты также содержат среднее и стандартное отклонение для справки. Для медианы приводится точный консервативный непараметрический 95% интервал по порядковым статистикам только при не менее чем шести независимых запусках. Этот интервал описывает разброс процессов внутри одной сессии, но не межсессионный дрейф. Повторите полный эксперимент как минимум в трёх новых сессиях и рассматривайте сессию как отдельную статистическую единицу; не смешивайте smoke-тесты и серии с разными параметрами/версиями кода. Для задержек батчей — p50/p95/p99 внутри запуска; это не замена статистике между независимыми запусками. Указывайте, что задержки относятся к батчу синтетической нагрузки, а не к пользовательскому HTTP-запросу.
7. Не делайте вывод «язык A быстрее языка B» только по этой программе. Она сравнивает давление на GC при заданной синтетической форме графа объектов, а не полезную производительность произвольного приложения.

Для первой серии можно использовать следующие параметры, затем увеличить или уменьшить их после пробного запуска:

```text
--warmup-batches 50 --batches 1000 --items 10000 --payload 128
```

Для сценария `large` уменьшите `items` и задайте крупный `payload`, например `--items 64 --payload 100000`; проверьте доступную память.

## 6. Как трактовать результаты

- `allocated_bytes_delta` — объём выделений за измеряемый интервал, а не объём оставшихся живых объектов. Go считает process-wide `TotalAlloc`, .NET — managed allocations процесса, Java — счётчик всех живых Java-потоков и отдельно поток бенчмарка. Не сравнивайте эти значения между платформами; в JSON/CSV указаны scope и `cross_platform_comparable=false`.
- `heap_used_after` / `heap_alloc_bytes_after` — состояние кучи в момент снимка; значение зависит от того, когда последняя сборка прошла.
- `heap_committed` и RSS — разные величины. Committed heap нельзя подменять физической памятью процесса.
- Счётчики GC не являются самостоятельной оценкой качества и не образуют общую межплатформенную шкалу: Go `NumGC` — циклы, .NET — отдельные поколения, Java — отдельные MXBean-коллекторы. Анализируйте каждый runtime отдельно.
- Суммарные паузы нужно анализировать вместе с числом сборок и профилем нагрузки. Распределение Go оценивается по дельте гистограммы `/sched/pauses/total/gc:seconds` за полный измеряемый интервал; p50/p95/p99 приближённые, восстановлены по bucket-границам. Индивидуальные паузы .NET получаются отдельным EventPipe запуском: полная длительность фиксируется от `GCSuspendEEStart` до `GCRestartEEStop`, а период полностью остановленного runtime — от `GCSuspendEEStop` до `GCRestartEEStart`; тип и поколение связываются с `GCStart`. Java распределение берётся отдельной узкой JFR-записью. Эти распределения имеют разный охват и условия измерения — не сравнивайте квантили пауз между runtime как эквивалентные показатели.
- `logical_nodes_per_second` и `payload_bytes_per_second` — интенсивность синтетической тестовой нагрузки, а не пропускная способность реального сервиса. `batch_latency_ms` характеризует время создания одного батча и включает работу аллокатора, прикладного кода и воздействие GC. Это не чистое время GC и не задержка реального HTTP-запроса.
- Основные графики показывают медиану между процессными повторами; усы обозначают IQR, а не доверительный интервал. В таблице 95% ДИ относится к генеральной медиане и вычисляется точно консервативным непараметрическим методом; при менее чем шести повторах конечный 95% интервал не показывается. Эти интервалы не включают различия между отдельными сессиями: не объединяйте несколько session ID в одну сводку и не делайте вывод о различии платформ только по одной сессии.
- В Windows Go измеряет каждый батч и всё измеряемое окно через `QueryPerformanceCounter`; на других ОС Go использует монотонный таймер. Значения p50/p95/p99 сравнивайте только после проверки поля `batch_latency_ms.timer` и достаточной длительности измеряемого окна.
- Темп узлов/с — интенсивность данной синтетической нагрузки; карточки с процентным рейтингом относительно Go удалены. Диагностические графики GC строятся отдельно для каждого runtime. Суммарные паузы Go/.NET и приблизительное MXBean elapsed Java не являются одной сопоставимой метрикой.
- Для Java используйте JFR/GC log для распределения пауз; MXBean elapsed time не подписывайте как STW-паузу. В отчёте GC-диагностика агрегируется по каждому runtime отдельно. Межплатформенные графики не строятся для счётчиков GC, аллокаций и пауз: у них различаются охват и семантика. Размер heap после GC — диагностический снимок, не RSS и не универсальная оценка физического живого набора.
- Для .NET `GC.GetTotalPauseDuration()` — сумма пауз управляемых потоков в основном запуске. Индивидуальные паузы записываются отдельно через EventPipe; для трассы проверяются счётчик потерянных событий и незакрытые интервалы.
- Для Go `PauseTotalNs` — суммарные STW-паузы. Распределение берётся из дельты `/sched/pauses/total/gc:seconds` за весь измеряемый интервал, а не из кольцевого буфера `PauseNs`; процентили оценочные, поскольку bucket histogram не содержит точных длительностей отдельных пауз.
- `WorkingSet64` внутри .NET JSON — точечный снимок, а не пик. Для стандартных повторов BAT использует внешний sampler: `memory_metrics.peak_working_set_bytes`, `average_sampled_working_set_bytes`, `initial_working_set_bytes` и `final_working_set_bytes`. Пик Windows берётся из PSAPI; среднее — из 50-мс выборок. Источник и число выборок сохраняются в JSONL/CSV. Среднее не является непрерывной интеграцией, а мониторинг может слегка влиять на планирование; интерпретируйте memory metrics отдельно от рейтингов производительности.

## 7. Ограничения сопоставимости

Тестовые структуры функционально похожи, но их физическое представление в памяти различается: размеры заголовков объектов, выравнивание, массивы ссылок, стратегия размещения и runtime overhead не одинаковы. Поэтому `payload_bytes_requested` — общий объём полезной нагрузки, а не предсказание фактического размера heap. Сопоставляйте его с runtime allocation counters, но не ожидайте побайтного равенства.

Текущий набор однопоточный. Это упрощает сопоставление allocation counters и изолирует эффекты времени жизни объектов, но не покрывает поведение GC при многопоточной серверной нагрузке. Для статьи следует прямо указать это ограничение. Если область применения статьи — многопоточные серверы, нужно добавить второй профиль с параллельными producer-потоками и одинаковым числом рабочих потоков на всех платформах.

Новые результаты бенчмарков имеют `schema_version=2`; `tools\summarize.py` отказывается объединять данные разных версий. Исходные JSONL/CSV старых экспериментов остаются без изменений и не должны смешиваться с результатами v2.

## Пакетная обработка STW-пауз Java из JFR

Для анализа JFR-записей используйте только верхнеуровневое событие `jdk.GCPhasePause`. Не суммируйте вместе с ним `jdk.GCPhasePauseLevel1`, `Level2` и `Level3`: это вложенные фазы, что приведёт к двойному учёту.

После записи JFR для сценариев выполните из корня проекта:

```bat
tools\process_java_jfr.bat
```

Или обработайте только один сценарий:

```bat
tools\process_java_jfr.bat transient
```

Будут созданы три файла в `results\jfr-analysis`:

- `pause_events.csv` — каждая отдельная STW-пауза с временем начала, GC ID и длительностью;
- `per_run_summary.csv` — число пауз, сумма, среднее, p50, p95, p99 и максимум для каждого независимого запуска;
- `scenario_summary.csv` — медиана и межквартильный диапазон показателей между независимыми запусками, включая распределения p50/p95/p99 по запускам.

Сценарная сводка использует независимые запуски как статистические единицы. Для публикации предпочтительно сравнивать между платформами медианы и межквартильные интервалы метрик по повторам, а не считать каждую паузу независимым экспериментальным запуском. В `jfr_pause_report.py` и `jfr_pause_batch.py` используется один метод процентилей — линейная интерполяция PERCENTILE.INC.

p95/p99 распределения отдельных пауз следует интерпретировать осторожно, если в записи мало событий. При малом числе пауз p99 практически совпадает с максимумом и не является устойчивой оценкой хвоста распределения.

В .NET поле `gc_pause_share_percent_process_cumulative` является накопительным с момента загрузки runtime и включает прогревочные/подготовительные сборки; для доли пауз внутри конкретного теста используйте `gc_stw_pause_total_ms_delta / elapsed_ms * 100`, а не это накопительное поле. Go `PauseTotalNs` — runtime-сумма STW-пауз, .NET `GC.GetTotalPauseDuration()` — сумма пауз управляемых потоков, а Java JFR `jdk.GCPhasePause` — инструментированные события HotSpot. Источники и условия измерения различаются, JFR может вносить overhead; даже суммарные значения не следует трактовать как строго сопоставимую межплатформенную метрику. JFR нужен для отдельного анализа Java, не для общего рейтинга пауз. См. [Go runtime.MemStats](https://go.dev/src/runtime/mstats.go), [Microsoft GC.GetTotalPauseDuration](https://learn.microsoft.com/en-us/dotnet/api/system.gc.gettotalpauseduration?view=net-10.0) и [Oracle JFR GC events](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshoot-performance-issues-using-jfr.html).


Сумма `duration_ms` событий `jdk.GCPhasePause` — суммарное время приостановки приложения в пределах записанного интервала. Для расчёта доли времени пауз используйте `total_pause_ms / measurement_wall_time_ms * 100`; wall time должен относиться к тому же измеряемому интервалу, а не ко всему времени жизни JVM.
