# GC Benchmark Pack: Go, .NET 10 и Java

Набор программ и сценариев для **экспериментального исследования поведения сборщиков мусора (Garbage Collector, GC)** в Go, C#/.NET 10 и Java/HotSpot.

Проект предназначен для воспроизводимых сравнительных экспериментов с синтетическими профилями времени жизни объектов. Он не является универсальным тестом производительности языков и не моделирует произвольное промышленное приложение.

## Назначение и область применения

Проект позволяет:
- запускать одинаковые по логике сценарии нагрузки в трёх средах выполнения;
- сохранять результаты отдельных запусков в машиночитаемом формате;
- собирать дополнительные диагностические данные о паузах GC;
- анализировать распределения задержек батчей, показатели кучи и системную память;
- повторять эксперимент с фиксированными версиями runtime и параметрами конфигурации.

**Границы интерпретации.** Счётчики аллокаций, число сборок и распределения пауз имеют платформенно-зависимую семантику. Они не должны автоматически объединяться в единый межплатформенный рейтинг. Набор нагрузки однопоточный на уровне прикладного кода; он не заменяет исследование многопоточных серверных приложений.

## Быстрый запуск (Windows)

В корне проекта выполните:

```bat
RUN_ALL_GC_EXPERIMENTS.bat
```

Либо задайте параметры явно:

```bat
RUN_ALL_GC_EXPERIMENTS.bat [runs] [items] [batches] [payload]
```

Значения по умолчанию: `10 10000 1000 128`. Скрипт проверяет наличие Python 3.10+, Go, .NET 10 SDK, JDK 21+ (включая `javac` и `jfr`) и `dotnet-trace`, затем запускает стандартную матрицу сценариев, отдельные диагностические серии и формирует отчёты. Установка .NET-утилиты при необходимости:

```powershell
dotnet tool install --global dotnet-trace
```

Каждый полный запуск сохраняется в отдельном каталоге `results/run_...`; существующие результаты не должны перезаписываться. Файл `experiment-info.txt` содержит сведения о среде и параметрах конкретного запуска. Чтобы пропустить дополнительную серию массивов 1 MiB, в CMD перед запуском задайте:

```bat
set SKIP_LARGE_OBJECT_SERIES=1
```

Подробности автоматического запуска, ручной сборки и команд для отдельных runtime приведены в [руководстве по запуску](docs/methodology.md).

## Экспериментальные сценарии

| Сценарий | Моделируемый профиль |
|---|---|
| `transient` | Большой поток краткоживущих объектов |
| `retained` | Доля объектов сохраняется достижимой между батчами |
| `graph` | Граф объектов с циклическими и перекрёстными ссылками |
| `large` | Создание и освобождение массивов заданного размера |
| `mixed` | Сочетание удерживаемых объектов и краткоживущих буферов |

Параметр `payload=128` не создаёт объекты LOH в .NET или humongous-объекты G1. Для таких исследований предусмотрена отдельная серия крупных массивов размером 1 MiB; пороги и параметры JVM/GC должны фиксироваться в протоколе. Точное описание сценариев и параметров находится в [методике эксперимента](docs/methodology.md).

## Измеряемые показатели

Проект сохраняет показатели аллокаций и кучи runtime, число и длительность сборок, задержки батчей, логическую интенсивность нагрузки и метрики Working Set/RSS. Диагностические источники различаются:

- Go: runtime counters и гистограмма `/sched/pauses/total/gc:seconds`;
- .NET: GC API для базовых показателей и EventPipe для отдельных пауз;
- Java: ThreadMXBean/MXBean для runtime-показателей и JFR для диагностических событий пауз.

**Ключевое методологическое ограничение:** одинаковые названия полей не гарантируют одинаковый охват. В частности, счётчики аллокаций Go, .NET и Java имеют различную семантику; индивидуальные паузы Go, .NET и Java также получают разными способами. Межплатформенные квантили пауз и счётчики аллокаций не следует трактовать как эквивалентные величины. Полная матрица метрик и правила интерпретации приведены в [описании метрик](docs/metrics.md).

## Протокол и воспроизводимость

Для корректного эксперимента необходимо:
1. Зафиксировать аппаратную платформу, ОС, архитектуру, версии компиляторов/runtime и параметры GC.
2. Использовать одинаковые логические параметры сценариев и заранее определить сравниваемые конфигурации.
3. Выполнять независимые повторы в отдельных процессах и сохранять исходные JSONL/CSV, а не только агрегаты.
4. Не смешивать данные разных версий схемы, конфигураций runtime и экспериментальных сессий.
5. Представлять медиану и межквартильный размах (IQR), отдельно указывать доверительные интервалы и число независимых повторов.
6. Отделять базовые измерения времени от инструментированных диагностических запусков JFR/EventPipe.

Рекомендуемый протокол, статистическая обработка и ограничения описаны в [методике эксперимента](docs/methodology.md) и [описании диагностических трасс](docs/diagnostics.md).

## Ограничения исследования

- Прикладная нагрузка создаётся одним основным потоком/горутиной; параллельная работа внутренних потоков GC возможна. Результаты не характеризуют многопоточные серверные нагрузки.
- Физическое представление структур, заголовки объектов, выравнивание и накладные расходы runtime различаются. `payload_bytes_requested` отражает заданную полезную нагрузку, а не фактический размер объектов в куче.
- Принудительные сборки, выполняемые в подготовительных/диагностических фазах, не являются частью измеряемой нагрузки; их наличие и семантика зависят от runtime.
- Внешний мониторинг памяти может влиять на планирование процесса. Пиковый Working Set в штатном сборщике относится ко всему времени жизни процесса, включая прогрев и очистку, а не только к измеряемому окну.
- Синтетический тест показывает поведение runtime при заданной структуре нагрузки. Он не позволяет без дополнительных экспериментов заключить, что один язык или runtime быстрее другого для произвольных приложений.
